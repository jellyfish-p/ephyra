# Ephyra 架构与分阶段验收计划

> **状态：首版设计基线已获用户整体确认，尚未实现。** 已确认产品规则以 [首版需求基线](./mvp-scope.md) 为准。本文把这些决定落成工程方案；标为“默认”的项目属于用户授权收敛的可逆细节，不代表已完成压测或安全验证。

## 1. 设计树与部署形态

```text
正式竞赛 / 技术自主 / ≤100 人试运行
├─ 全站账号 → 多组织隔离 → 组织成员 / 组织外参赛者
├─ 比赛
│  ├─ 赛制：ACM / OI / IOI（整份最优）
│  ├─ 报名类型：个人 / 单场队伍，与赛制独立
│  └─ 统一时钟 → 允许晚报名 → 报名生效后冻结队员
├─ 评测
│  ├─ Go ephyra-judge → 直接 go-sandbox → 独立 Linux 宿主
│  ├─ 基础 Hydro 导入 → 规范化题目配置 → 内置比对 / testlib / 交互
│  └─ 系统池 / 组织独享池 → 组织级优先路由 → 满载排队
└─ 正确性
   ├─ PG 权威 + Outbox + Redis Streams
   ├─ 版本化题目数据 + 独立评测尝试 + 整批重测切换
   └─ 失联人工处置 + 故障阻止自动公布 + 服务端统一可见性策略
```

```text
浏览器
  │ 同源 HTTPS，安全会话 Cookie
  ▼
Nuxt ── /api ── Go 模块化单体
                  ├─ Gin：业务请求、授权下载、事件订阅
                  ├─ gRPC：节点主动连接、心跳、派发、结果回报
                  ├─ Outbox 发布 / Streams 消费 / 调度
                  ├─ PostgreSQL：业务、会话、任务、尝试、版本、Outbox
                  ├─ Redis Streams：可重复的分发通知
                  ├─ 私有 S3 兼容存储：版本文件、源码、结果附件
                  └─ 邮件发送能力：验证邮箱与账号恢复
                           ▲
                           │ 节点主动出站建立 TLS gRPC 流
                  ephyra-judge（系统池或组织独享池）
                     └─ 编译 / 判题编排 / go-sandbox
```

首版业务后端是一个部署单元，内部划分 Module，不拆账号、比赛、调度微服务。Nuxt、业务进程、数据设施和评测宿主是不同角色；评测端不得与业务密钥或数据库共享操作系统环境。首版不宣称业务控制面已经支持多副本高可用。

## 2. 仓库与协议所有权

以下仅为布局方案，**未创建这些实现目录或评测端仓库**：

```text
ephyra/
  web/                 Nuxt
  server/              Go 业务后端
  protocol/            唯一权威的版本化 .proto 与生成代码发布入口
  docs/
ephyra-judge/          独立仓库
  cmd/ephyra-judge/
  internal/            传输、工作区、编译、执行、校验、回报
```

协议只维护一个源头；主仓库发布可引用版本，评测端固定依赖该版本，不复制一份自行演化的 proto。连接握手协商协议版本与执行能力；不兼容的主要版本拒绝派发。编译器、标准库、参数、架构、sandbox 配置组成可识别的执行配置，任务引用配置标识，而非接收选手自定义编译命令。

## 3. Module 与 Interface

以下是职责及可测试契约，不是提前生成的一层层 CRUD 包装。

| Module | 对外 Interface 的职责 | 内部隐藏的复杂度 |
| --- | --- | --- |
| Identity & Access | 解析身份、验证组织／比赛范围、形成允许的视图 | 会话、邮箱验证、成员关系、访问控制、敏感操作审计 |
| Contest | 创建与配置比赛、报名、邀请确认、按阶段接收参赛操作 | 两类报名主体、审核、名单冻结、统一时钟、公开策略 |
| Problem Package | 验证并导入题包，产出规范化配置与不可变文件引用 | 解包安全、Hydro 字段解释、子任务、checker、interactor、版本 |
| Submission | 接受一次作答，返回稳定提交标识和接收结果 | 截止判定、源码持久化、幂等接收、任务与 Outbox 事务 |
| Judging | 选择授权资源、委派尝试、接收回报、人工重新派发 | 优先级、槽位、节点认证、租约、重复消息、过期结果、文件授权 |
| Scoring & Publication | 计算成绩及按受众读取榜单／反馈，切换重测版本 | 赛制算法、有效结果选择、封榜、OI 隐藏、发布完成条件 |

控制器只调用这些 Interface，不到处直接更新“提交状态”“已通过题数”或“当前榜单”。评分函数用确定的提交顺序、规则和有效结果计算，可用表驱动测试验证；GORM 模型不直接作为浏览器或节点响应。

题包未来扩展的 Seam 是“包内容 → 规范化配置”。当前只实现 Hydro 导入函数；第二种格式出现后再提取公共 Adapter 契约，不先搭动态插件系统。普通校验与 testlib 等真实差异放在判题实现内部，不把上游 Hydro 对象散布到业务调用者中。

## 4. 领域记录与不变量

建议记录范围：账号与会话、组织与成员、题目、评测数据版本、比赛题目、比赛、参赛报名、参赛主体与队员快照、提交、评测任务、评测尝试、重测批次、资源池与节点、路由版本、Outbox、审计记录。具体表名、索引及迁移在实现阶段设计，不把词汇表当数据库结构。

必须保持：

1. 个人、队伍和实际提交人分别表达；不能以 user_id 同时代替三者。对同场参赛主体唯一性与队员确认做事务约束。
2. 提交内容和接收顺序不可被重测改写；“最后一次”“第一次通过”按服务端接收顺序计算，不按节点完成顺序。
3. 比赛题目显式引用评测数据版本。题库更新不能静默改变已运行比赛的判定依据。
4. 任务描述需要完成的评测工作，尝试描述一次具体委派。首次派发产生初次尝试；失效后只有获授权的人工操作能重新派发并产生新尝试。
5. 每次尝试固定提交、数据版本、执行配置、节点和资源池；回报必须完整匹配这些引用。失效尝试不能更新有效计分结果。
6. 分数使用精确表示，不用二进制浮点误差打破“同分并列”；输入精度超出明确支持范围时拒绝，而非静默舍入。没有隐藏的时间或提交次数 tie-break。
7. 会话和组织身份不能从客户端传入的 org_id 推导可信授权。对象访问、对象存储下载、节点任务、公开视图都执行同一范围校验。
8. 数据库元数据引用不可变对象。文件上传及完整性检查完成后才建立可用引用；未被事务引用的孤立对象可异步清理，不能因失败事务暴露半成品题包。

## 5. 从提交到结果：权威在 PostgreSQL

1. 服务端完成身份、报名、邮箱、时间、语言及请求大小检查，接收完整源码。比赛时间以服务端记录的接收时刻为准；持久化成功前不返回“已接收”。
2. 同一数据库事务写入 Submission、待评测工作和 Outbox 事件；源码大对象已完整落到私有存储，事务引用其固定内容标识。
3. Outbox 发布器向 Stream 投递事件，允许重复投递；事件引用持久记录，而不是把 Redis 当唯一任务副本。
4. 消费者将事件持久化处理为“待调度”或识别为已处理后 ACK。**消息 ACK 不是程序评测完成。** 没有空闲槽位时，工作仍保留在 PostgreSQL 等待后续容量变化。
5. 调度器在事务中按组织路由、能力和槽位委派尝试，再通过节点现有 gRPC 流发送。连接发送失败也不能假定节点未收到后自动创建另一个尝试。
6. 节点下载被授权的固定版本文件、验证完整性，在受限环境完成编译和运行，回报归一化状态、逐点结果和资源指标。
7. 服务端校验尝试身份、版本、节点、有效期、结果结构及重复回报；正常终态幂等落库并更新对应的有效评分视图。
8. 超期、节点失联或协议／执行系统错误进入待管理员处理。管理员处理操作留痕，旧尝试失效后重新委派；不会改写原提交时刻。

Stream 事件丢失后的恢复依据持久任务和 Outbox 做对账，不要求把已完成的消息无限保存。消费恢复可以重投“通知”，但不能将已失败、等待管理员的工作自动恢复为新执行。具体 Streams 保留、ACK、重投与 Outbox 清理策略必须通过故障注入验证后锁定。

节点连接断开后的重连，只能核对仍有效的既有尝试并恢复允许的回报；已经失效的任务不会因为节点重新在线而自动重跑。重复派发只返回已有尝试状态，不再次启动程序；重启后无法确定是否已执行的尝试交由管理员处理，不猜测为“未执行”后重跑。重复回报内容不一致时拒绝覆盖并记录异常。节点重新报告空闲槽位前，必须对账并清理失效尝试的运行进程和工作区，避免释放账面槽位后实际资源仍被占用。

## 6. 调度与节点信任

- 服务端登记节点及其池归属，每节点独立凭据；只存储必要的安全校验材料，支持撤销与轮换，不给节点数据库、Redis 或 S3 管理凭据。
- 组织只能管理和使用获授权的资源池。组织自建节点不能自行把身份改为系统节点或其他组织节点。
- 池选择先过滤组织授权及任务所需执行能力，再按优先级从高到低尝试；同级可调度池负载均衡。
- 本级有健康兼容节点但全部忙时继续等待，不因为低优先级空闲就回退。所有级别均无可用资源则记录调度错误，由管理员处理。
- 工程默认：组织内按接收顺序等待，共享池在可调度组织间避免持续饥饿；同级池按可用槽位分配，槽位占用必须原子化。该默认不改变严格的池优先级。
- 每次派发记录使用的路由版本；修改组织路由不迁移正在执行的尝试，也不自动复活待人工处理任务。
- 节点身份认证只证明连接身份，不证明运营者诚实。组织自建节点能够接触送入的源码与测试数据，其结果可信度依赖组织对运营者的信任；首版不承诺可信硬件证明或抵抗恶意节点伪造本组织判定。

## 7. 重测与发布屏障

### 版本化重测

创建修正数据版本和重测批次时，明确该时点应重测的提交集合。随后新收到的提交使用目标版本，并标注版本；不通过不断把新提交塞进旧批次来制造永远无法完成的屏障。

旧版本仍是该题当前计分依据，榜单标记“重测中”；新结果先作为目标版本结果保存，不能逐条替换旧榜。个人反馈若展示新结果，必须注明版本与尚未计入当前榜单，避免将临时反馈误标为生效成绩。

批次内所有必需评测均形成正常终态后，在事务中切换该比赛题目的计分版本，并按同一目标版本重算。新版本下尚未完成的新提交仍是待评测，不能被当作 0 分。单题只允许一个待切换修订批次，连续修订须先显式处置前一批次。

### 自动公开／解封

“比赛已结束”不单独触发发布。还须确认该场所有应评测提交已有当前应生效版本的正常结果、无待切换批次、无待处理系统错误。CE／WA／TLE 可属于正常判定；节点故障、checker 崩溃、调度失败等不属于。

满足屏障后才执行 OI 自动公开、ACM 自动解封，以及已预先选择的源码公开。赛后再次修正数据时，已经披露的信息无法收回：保留已公开的旧版结果并标注重测，待批次完成后统一更正，不声称重新隐藏可以撤销历史披露。

## 8. 评测执行与保密

- 所有选手程序、编译过程、题包 checker 和 interactor 都要纳入受限执行；“组织管理员上传”不等于可以在宿主机直接运行。
- 编译、选手程序、checker、interactor 分别有明确角色、文件可见范围和资源上限。checker／interactor 自身故障与选手错误区分，不把前者结算为选手 WA。
- 拒绝越界路径、符号链接逃逸、解压炸弹和未经支持的配置；限制解压量、文件数、输出量、进程／线程、CPU、内存、墙钟时长及临时空间。
- 选手进程正常退出不等于答案正确，必须经过已选比对或 checker／interactor 协议判定。评测端不决定 OI／IOI 跨提交取分、ACM 罚时或公开时机；平台依据固定配置计算并校验分数，摘要与明细矛盾时不接受覆盖。
- 执行环境默认不允许任意网络、访问宿主文件、其他任务工作区或业务凭据。go-sandbox 启动成功不等于控制器或 seccomp 已生效，必须做实际隔离测试。
- gRPC 字段明确时间与内存单位，不复用一个含混的 time／memory 字段。比赛计时只用平台提交时刻，不用节点报告的本地时间。
- 节点缓存按内容及执行配置区分，不能仅用题号或文件名命中。编译缓存、运行目录和输出文件均需生命周期与清理策略。
- 不把原始 JudgeResult 或原始日志直接广播给浏览器。testlib 的错误文本可能包含期望输出，故选手侧仅输出允许的归一化状态和白名单详情；不得借 checker 日志绕过取消期望输出的决定。
- OI 隐藏、ACM 封榜、源码权限在服务端读取与实时事件出口统一执行，不能依赖 Nuxt 隐藏字段。敏感文件访问使用任务或用户范围的短期授权，不发放整个桶权限。

## 9. 已授权的可逆工程默认

这些是已确认的工程默认，不是已经测得的最佳值。调整它们不能改变需求文档中的业务与安全规则。

| 项目 | 首版默认 |
| --- | --- |
| Web 形态 | Nuxt 使用默认渲染能力，交互区客户端更新；同源 /api，权限与业务真相只在 Go；实时提示优先 SSE，断线后从授权读取恢复 |
| 会话 | Cookie 使用 HttpOnly、Secure、SameSite=Lax，状态变更做 CSRF 校验；会话可撤销；不使用 localStorage 存放长期凭据 |
| 账号恢复 | 使用已验证邮箱的单次、限时恢复流程；验证码／重置凭据不明文入日志，启用注册、登录、发信与提交限流 |
| 比对 | 支持精确文本与忽略空白的 token 比对；以显式配置为准，Hydro 字段与默认行为必须由兼容测试确定；不认识的规则拒绝导入 |
| 子任务兼容 | 仅实现已确认的全过得分规则；其他聚合、部分分协议、未实现的依赖配置明确拒绝，不能静默降级 |
| 同分展示 | 并列排名按竞争排名展示，例如 1、2、2、4；稳定的行展示顺序不能被当作额外名次依据 |
| 并发 | 首次验证每节点先设 1 个任务槽位；增加槽位前核验编译、交互双进程、内存和工作区隔离 |
| 健康与租约 | 初始目标心跳 10 秒、连续 60 秒无有效续约判失联；短暂断流先等待重连，失效后人工处置。必须经断网、慢执行和恢复测试校准，心跳不能被程序运行阻塞 |
| 任务标识 | 使用独立任务／尝试／版本标识与递增委派代次进行有效性校验，不以提交 ID 一个字段承担所有幂等与回报关联 |
| 运维 | 日志关联组织、比赛、提交、任务、尝试、版本、批次、池和节点；不记录完整代码、测试答案或认证凭据 |
| 数据变更 | 显式、可追踪的数据库迁移；不将生产 GORM 自动迁移当发布流程；历史计分记录不提供任意 CRUD 覆盖入口 |

精确速率、包大小、保留期、资源默认及性能阈值按首批题包和硬件基线测定后固定；无数据时不虚构吞吐量或延迟保证。邮件使用已确定验证／恢复需求所需的发送能力，具体提供方在配置阶段确认，不自建一个新的邮件产品。

## 10. 分阶段落地与退出条件

### 阶段 0：合规、契约和验证环境

- 锁定实际参考／移植的 Hydro 文件与版本、go-sandbox 版本、testlib、工具链及镜像来源；确认版权通知、许可证与发行义务。评测端新仓库 LICENSE 需在选定来源后明确确认，不能把根 MIT 直接复制过去作为授权结论。
- 在独立 Linux 验证宿主记录内核、cgroup 控制器、权限、挂载与编译环境；没有这些条件不进行不受信任程序验收。
- 固定首批 Hydro 子集兼容矩阵和正常／恶意题包夹具；定义自有协议版本、数据单位、身份、状态及幂等规则。
- 以稳定发行版验证 C++23、C17、C23 的实际编译与库能力，不以支持表某个版本号代替可部署发行物检查。

**退出条件：** 来源与许可无阻塞，必要运行限制实际有效，首批语言和题包契约有可运行的验收夹具。仅文档写出“使用 go-sandbox”不算通过。

### 阶段 1：评测垂直切片

- 先用固定任务验证编译 → 普通题 → SPJ → 交互 → 子任务 → 资源统计和清理。
- 验证 CE、WA、TLE、MLE、RE、checker／interactor 故障、死锁、输出爆量、fork bomb、越界文件与网络访问。
- 实现 gRPC 注册身份、心跳、有限授权文件访问、尝试回报与失效结果拒绝，不接收浏览器直接指定 shell 命令。

**退出条件：** 结果可重复，角色故障分类正确，工作区与宿主隔离成立，错误尝试不能污染后续任务。题包结构兼容不代替判题行为兼容。

### 阶段 2：持久任务和比赛闭环

- 实现账号／组织、题目版本、比赛配置、报名与队伍、提交事务、Outbox／Streams、池路由、评分、可见性和重测切换。
- Nuxt 完成注册／验证、组织申请、比赛报名与组队、题面与提交、个人结果、榜单及必要管理操作；不扩展为练习或社区产品。
- 先验收下面的确定性规则与故障矩阵，再优化吞吐量。

### 阶段 3：试运行准备

- 在记录硬件和题包负载的前提下，执行不超过 100 人的并发模拟赛、集中提交、封榜结束与重测压测。
- 演练数据库恢复、对象完整性恢复、Redis 重建、节点离线、业务进程重启、凭据撤销与日志审计。
- 明确可接受的延迟、积压和人工处置时间；发布部署、备份、故障处理与许可说明后，再进入小范围真实比赛。

## 11. 必须通过的验收矩阵

| 场景 | 期望 |
| --- | --- |
| OI 同题 30 → 80 → 60 | 最终 60；赛中没有隐藏测试反馈 |
| OI 最后一份为 CE | 使用最后一份的正常 CE 结果，不回退上一份成绩；系统故障则不按 CE 或 0 分结算 |
| IOI 两次子任务 (50,0)、(0,50) | 最终 50，不拼成 100 |
| 子任务一部分点通过 | 该子任务 0 分；其他子任务照既定规则计算 |
| ACM 两题均在 1:29 通过 | 耗时项合计 2 分钟，而非合计后取整为 3 |
| ACM 1:30 通过、此前一次 WA 和一次 CE | 耗时项 2 分钟，加一次配置错误罚时，不计 CE |
| 评测结果乱序返回 | 最后提交、首次通过均按接收顺序确定 |
| 单人队伍／晚报名 | 进入队伍榜；使用统一时钟，队员名单按报名生效点冻结 |
| 组织外用户获准参加一场比赛 | 只能获取该场必要权限，不能读取组织其他题库或任务 |
| 高优先级满载、低优先级空闲 | 等待高优先级，不降级 |
| 本级不可用／所有级别不可用 | 前者才尝试下一级；后者调度错误等待管理员 |
| 重复 Stream 消息与重复结果 | 不重复执行、不重复计分、不自动创建新尝试 |
| 节点失联后恢复／旧结果迟到 | 失效任务不自动重跑；旧尝试不得覆盖新尝试或新版本 |
| 重测批次部分完成或部分系统错误 | 保留旧计分版本并标注重测；不半批切换或自动公布 |
| 重测期间有新提交 | 明确绑定目标版本，个人临时反馈与生效榜单可区分，发布仍等待应完成工作 |
| 比赛结束但一份提交系统故障 | OI 不自动公开、ACM 不自动解封、受完成条件约束的源码不公开 |
| 修改对象 ID／组织 ID／池 ID | 服务端拒绝越权，不能借下载地址或 gRPC 绕过 |
| OI API／SSE、ACM 封榜、testlib 错误文本 | 不能绕过隐藏、封榜或期望输出保密策略 |
| 预先不公开源码／匿名访客 | 前者不会赛后自动全站公开；后者不能读取公开源码 |
| 私有题包解压、编译和程序逃逸尝试 | 不能访问宿主秘密、其他任务或无限消耗资源；拒绝或正确分类故障 |
| Redis 丢失／业务进程重启 | 能从持久记录对账恢复待调度工作，不丢已接收提交，也不自动重跑失效尝试 |
| 备份恢复 | 数据库中的版本引用与私有对象保持对应，历史结果和源码权限可复核 |

上述矩阵是验收要求，**目前没有实现或执行这些测试**。设计基线已确认，后续仍须按阶段进入实现与验收；任何新权限、新赛制、额外外部服务或许可证调整仍另行确认。
