# Ephyra 首版需求基线

> **状态：首版设计基线已获用户整体确认。** 本文汇总设计访谈的当前结论，取代早期轮次中已被修正的表述；不表示已经开始实现、创建评测端仓库或完成性能／安全验证。
>
> 领域用语见 [CONTEXT.md](../../CONTEXT.md)，工程默认与验收关卡见 [架构与验收计划](./architecture.md)。研究材料是证据，不会覆盖用户明确选择的产品规则。

## 1. 目标与首版规模

- 面向正式竞赛，自建目标是技术栈与长期维护自主。
- 首版交付门槛为小范围真实使用，不是仅能演示的学习原型。
- 首场实际规模尚未确定，先按不超过 **100 名同时参赛者**规划。这不是已验证的容量承诺，也不是累计账号数上限。
- 没有必须赶上的比赛日期；按验证阶段推进，通过模拟赛后才用于真实比赛。

## 2. 账号、组织与授权

- 全站统一账号，本地账号密码登录，任何人可注册；验证邮箱后才能报名和提交。
- 未验证账号可登录并查看获准公开的内容，不因此获得组织或比赛权限。
- 浏览器采用 Go 后端管理的可撤销会话，使用 HttpOnly、Secure、SameSite Cookie 和 CSRF 防护；浏览器会话与评测节点凭据分离。
- 单实例支持多个隔离组织，各自拥有题库、成员和管理员；组织仅由站点管理员创建。
- 用户申请加入组织，由组织管理员审核；一个组织的权限不延伸到其他组织。
- 首版不支持站内跨组织题目共享。
- 每场比赛可选择是否允许组织外的站点用户参赛；外部参赛不产生组织成员身份，也不开放组织其他题库或比赛。
- 每场比赛可选择报名自动通过或由比赛管理员审核。成员审核与比赛报名审核是不同过程。
- 未明确授予的资源访问默认拒绝；不因知道对象 ID、属于同站点或能建立节点连接就获得资源权限。

## 3. 比赛、报名与队伍

- 赛制为 ACM、OI、IOI 三种；报名类型为个人或队伍，**二者独立选择**。
- 一场比赛只有一种赛制和一种报名类型，不混合个人与队伍。
- 报名类型创建后不可修改；赛制仅开赛前可改，开赛后冻结。
- 所有参赛者使用统一开赛和结束时间。允许开赛后报名，晚加入不补时，ACM 耗时仍从统一开赛时刻算起。
- 队伍只属于单场比赛，允许 **1～N 人**，N 按比赛配置；人数不足额和单人队伍同样进入队伍榜。
- 队员使用独立账号。选手建队，由队长邀请、队员确认；同一账号在同一比赛最多属于一个参赛主体。
- 队伍报名生效时冻结名单；开赛前可撤回、修改后重新报名并重新审核，开赛后已报名队伍不换人。
- 队员可提交，成绩归队伍，同时保留实际提交人。队伍报名以整队为主体，所有成员必须满足该场准入条件。

## 4. 计分规则

| 项目 | ACM | OI | IOI：Ephyra 产品口径 |
| --- | --- | --- | --- |
| 单题成绩 | 是否通过 | 同题最后一次提交 | 同题总分最高的一份提交 |
| 排名 | 通过题数降序、总罚时升序 | 总分降序，同分并列 | 总分降序，同分并列 |
| 跨提交子任务拼分 | 不适用 | 不允许 | **不允许** |
| 赛中本人反馈 | 正常评测反馈 | 只反馈编译状态，不公开隐藏测试结果 | 实时反馈分数与允许展示的详情 |

OI／IOI 内部均使用加权子任务：子任务所有测试点通过才获得该组全部分数，否则为 0；单次提交总分为各子任务分数之和。

### ACM 罚时

- 每道通过题的罚时 = 首次通过提交距统一开赛时刻的耗时 + 此前选手错误提交次数 × 配置罚时。
- 每次错误提交的罚时分钟数可配置；工程默认值为 20 分钟。
- WA、TLE、MLE、RE 等选手错误计入规则；CE 与系统故障不计罚时；未通过题不累计罚时。
- 每题耗时**分别四舍五入到分钟**后再相加；1:29 为 1 分钟，1:30 为 2 分钟，不能先合计再取整。
- 同通过题数、同罚时并列；重测不增加提交次数，也不改变原提交时间。

### 不宣称严格官方 IOI 兼容

两次提交分别得到子任务分 `(50, 0)`、`(0, 50)` 时，本项目 IOI 最终为 **50 分**，不是 100 分。已核实的官方 IOI 规则采用逐子任务跨提交取最高，与本项目有意选择不同，见 [ADR-0004](../adr/0004-ioi-whole-submission-score.md)。

## 5. 反馈、榜单和源码公开

- 比赛管理员可选择展示逐测试点状态或仅子任务状态；该开关不能突破赛制与阶段限制。
- OI 赛中仍只反馈编译状态，粒度开关在赛后公开阶段生效。
- IOI 赛中按所选粒度反馈；是否公开实时榜单单独配置，不影响本人分数反馈。
- ACM 支持按比赛配置封榜时长，也可关闭。封榜不停止评测，管理员可看实时结果，本人仍可看自己的合法评测详情；公开榜和其他公开接口不能泄露他人新增成绩。
- OI 结束且全部评测完成后自动公开成绩与允许的详情；ACM 在同样条件下自动解封，不要求首版滚榜动画。
- 系统故障、调度失败、未完成评测及未完成重测会阻止“全部评测完成”，不能当 0 分或选手错误结算；正常 CE／WA／TLE 等已判定结果与系统故障不同。
- **取消选手侧期望输出展示**，不提供赛中或赛后的此项开关；公开样例及管理员维护数据不在此取消范围内。
- 每场在开放报名前选择是否赛后公开源码，并告知报名者；不得在参赛后临时扩大原本保密代码的公开范围。
- 选择公开的比赛，在结束且全部评测完成后，源码可由**已登录站点账号**查看，匿名访客不可查看。
- 赛中及未选择公开的比赛，源码采用最小访问基线：提交者、同队队员、本场授权管理员；不向其他参赛主体开放。

## 6. 题包、题型与语言

- 必需能力：普通批处理、SPJ、交互题。SPJ 是输出校验，不等同于运行中交互。
- 首版兼容基础 Hydro 题包结构的明确子集；保留扩展其他格式的空间，不承诺 Hydro 全功能兼容或首版多格式实现。
- 自定义校验器与交互程序采用 testlib 风格协议；普通题提供内置比对。未支持配置明确报错，不静默改变语义。
- 首版选手语言：**C++23、C17、C23**。C++26 暂缓，且不默认加入 C++17/20、Python、Java、Go 或 Rust。
- C++23 使用已发布稳定工具链的已验证配置，不使用开发分支追逐特性，不承诺完整标准和标准库覆盖。
- 编译器、标准库、参数和执行环境需验证后固定并公开限制；同一比赛中的同一语言配置只派往匹配该配置的节点，不能仅凭节点声明“有 g++”就视为相同环境。

## 7. 提交、版本与故障

- 提交是一次作答递交；评测尝试是执行行为。人工重新派发、重测均不产生新的选手提交。
- 修正比赛题目测试数据必须生成新版本，并显式对该题在本场的全部相关提交重测，不原地覆盖后只影响新提交。
- 整批重测完成后统一切换计分结果；期间保留旧榜并标注重测中，不逐条混用版本。新提交也绑定明确版本。
- 节点领取任务后失联，**不自动重派**，一律由管理员处理。
- 网络重连、消息重复、结果回报重传不是重新执行评测的授权；旧尝试的迟到结果不能覆盖后续尝试或新数据版本结果。
- 不将系统错误包装成 WA／TLE／0 分，也不自动退回上一份提交成绩来掩盖故障。

## 8. 资源池与路由

- 同时支持系统评测资源池、组织独享评测资源池；独享池由组织自行部署和运营。
- 开源终端不等于可信节点。节点只能访问授权任务所需数据；组织自建节点不能取得其他组织任务或自行加入系统池。
- 路由仅在**组织级**配置，所有比赛统一使用，不提供比赛级覆盖。
- 管理员配置多个池及优先级；同优先级负载均衡，本级全部不可用才使用下一级。
- 满载但可排队仍属可用，应等待高优先级池；离线、禁用或无所需执行能力才属不可用。
- 所有级别都不可用时报告调度错误，等待管理员重新分配，不静默换到未授权的池。

## 9. 技术与交付选择

| 领域 | 已确认选择 |
| --- | --- |
| 前端 | Nuxt |
| 业务后端 | Go + Gin + GORM，模块化单体，不拆首版业务微服务 |
| 主数据库 | PostgreSQL，任务状态唯一真相 |
| 分发 | 事务 Outbox + Redis Streams；消息重投不触发重新评测 |
| 文件 | 私有 S3 兼容对象存储，版本化引用与授权下载 |
| 浏览器认证 | 后端可撤销会话 + 安全 Cookie + CSRF 防护 |
| 评测端 | Go 重写 ephyra-judge，直接集成 go-sandbox，不调用独立 go-judge 服务 |
| 节点通信 | 节点主动建立 gRPC 流；TLS + 每节点可撤销、可轮换凭据，不做首版 mTLS |
| 评测部署 | 独立 Linux 宿主／虚拟机，与业务后端及数据库隔离 |
| 仓库 | 主仓库包含 Nuxt、Go 业务及版本化协议规范；ephyra-judge 确定独立仓库，使用发布版本协议 |

基于 Hydro 源码的 Go 移植／重写不自动消除原许可义务。用户接受 AGPL 组件及相应义务，但具体文件、依赖与组合发行边界仍需核实；不依据语言转换、仓库分离或网络协议宣称许可问题消失。**根 MIT LICENSE 未修改**，未创建评测端仓库或远程仓库。

## 10. 明确延期

C++26、虚拟赛、独立赛后练习系统、题解／讨论社区、自动代码查重、hack、提交答案题、多格式题包实际实现、跨组织题目共享。首版不以扩展性为由提前实现这些功能。

## 11. 已授权默认与验证保留项

用户授权：不改变已确认业务、安全及持久化语义的可逆工程细节，可采用保守默认并记录。新增外部服务、新权限、赛制变化、许可证变化仍需单独确认。具体默认列在 [架构与验收计划](./architecture.md)，不是隐藏需求。

整体确认之后，仍须先验证并锁定：工具链发行物与镜像、Hydro 子集精确兼容矩阵、go-sandbox 运行条件、Redis／S3 实际发行产品及许可、邮件发送配置、资源与故障阈值、备份恢复和 100 人模拟赛负载。**这些是实现与上线验收关卡，不是已经通过的测试。**
